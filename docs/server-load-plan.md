# План устойчивости сервера при 100 одновременных игроках

## Цель и границы

Цель — обеспечить предсказуемую работу чата и PvP при **100 одновременно подключённых игроках** на одном экземпляре приложения, а затем подготовить безопасный путь к горизонтальному масштабированию. Этот документ — план работ, а не утверждение, что текущая реализация уже выдерживает такую нагрузку.

В первый этап входят WebSocket-соединения, синхронизация позиций, мировой и личный чат, группы и PvP. Маркет, Telegram polling и фоновые задачи участвуют в нагрузочном тесте как сопутствующая нагрузка, но не являются главным объектом оптимизации.

## SLO и критерии приёмки

Проверять на production-подобном стенде с PostgreSQL и теми же лимитами CPU/RAM, что у боевого сервиса.

| Показатель | Цель на ступени 100 игроков |
| --- | --- |
| Доставка сообщения мирового чата | p95 ≤ 200 мс, p99 ≤ 400 мс |
| Доставка подтверждённого PvP-удара цели | p95 ≤ 120 мс, p99 ≤ 250 мс |
| Задержка event loop | p99 ≤ 50 мс |
| Успешные WebSocket-соединения | ≥ 99,5% за прогон |
| Неожиданные разрывы соединений | < 0,5% за 30 минут |
| Ошибки HTTP 5xx и обработчиков WS | < 0,1% событий |
| Потерянные принятые сообщения чата/PvP | 0 |
| Память после выхода всех ботов | возвращается к уровню не выше baseline + 10% |

Замер доставки ведётся от времени отправки клиентом до получения целевым клиентом. Отдельно фиксируется серверное время обработки, чтобы отличать проблемы приложения от сетевой задержки.

## Что сейчас создаёт риск

1. **Блокировка event loop базой данных.** `AsyncLikeSession` имеет асинхронный интерфейс, но внутри выполняет синхронные SQLAlchemy/psycopg2-вызовы. Авторизация WebSocket читает прогресс и карму из БД, а завершение PvP синхронно записывает статистику. Пока такой запрос ждёт БД, чат, удары и heartbeat всех игроков в том же процессе также ждут.
2. **Квадратичная рассылка мира.** Каждые 100 мс для каждого клиента заново формируется полный список остальных игроков локации. При 100 игроках в одной локации это 99 000 сериализуемых записей игроков в секунду, не считая сетевых копий.
3. **Последовательная отправка.** `broadcast` и цикл мира ожидают `send_json` каждого сокета по очереди. Один медленный клиент способен увеличить задержку для следующих клиентов; индивидуальных очередей и политики backpressure нет.
4. **Линейный поиск игроков.** Поиск `online(uid)` проходит по всем соединениям. Он находится на горячем пути групп и PvP и повторяется внутри циклов.
5. **Состояние хранится только в памяти процесса.** Клиенты, история чата, группы, приглашения, rate limit и PvP cooldown локальны. Запуск второго процесса немедленно разделит мир и позволит обходить часть ограничений.
6. **Нет измеримого baseline.** `/health` сообщает только факт работы процесса; нет метрик задержки цикла, размера очередей, времени SQL, объёма рассылки и причин отключения.
7. **Рост служебных словарей.** Записи `last_seen`, приглашений, PvP-пар и счётчиков убийств не имеют общей периодической очистки, поэтому длительно работающий процесс может постепенно накапливать состояние.

## Целевой профиль нагрузки

Один 30-минутный прогон должен моделировать не просто 100 открытых сокетов, а активную игру:

* плавный набор 0 → 100 подключений за 2 минуты, затем 25 минут стабильной нагрузки и одновременный выход;
* 100 сообщений `pos` в секунду суммарно в обычном режиме и короткие пики до 300/с;
* 20 активно сражающихся пар, суммарно до 60 PvP-ударов/с;
* 10 сообщений мирового чата/с и 10 личных сообщений/с в пике;
* 25 групп по 4 игрока;
* 5 сохранений/с и 2 чтения профиля/рейтинга в секунду как фоновая HTTP-нагрузка;
* минимум 10% клиентов с искусственной задержкой чтения 500–1500 мс и один клиент, полностью переставший читать;
* отдельный сценарий «худшего случая»: все 100 игроков в одной локации.

Для воспроизводимости генератор хранит seed, сценарий, размеры сообщений и гистограммы end-to-end latency. Telegram `initData` для теста выдаётся только стендовым механизмом и никогда не ослабляет production-аутентификацию.

## Этап 0. Наблюдаемость и baseline

Сначала измеряем текущую систему, иначе невозможно доказать улучшение.

1. Добавить endpoint метрик, доступный только внутренней сети или защищённый токеном:
   * число активных и аутентифицированных WebSocket;
   * входящие события по типу и отклонённые события по причине;
   * длительность обработки `chat`, `pvp`, `pvp_dead`, `pos`;
   * длительность SQL и занятые соединения пула;
   * event-loop lag;
   * размер и возраст самого старого элемента каждой исходящей очереди;
   * отправленные байты, ошибки отправки и причины закрытия WS.
2. Ввести correlation/event ID в структурированные логи без текста личных сообщений и без `initData`.
3. Подготовить нагрузочный клиент (например, Locust с WebSocket-клиентом или k6) и сохранить baseline-отчёт для 25, 50 и 100 игроков.
4. Настроить алерты: event-loop lag p99 > 100 мс, очередь клиента > 80%, SQL pool wait > 100 мс, доля ошибок > 1%, неожиданный рост памяти.

**Выход этапа:** воспроизводимый тест и отчёт с CPU, RAM, трафиком, latency и профилем CPU. Никакая оптимизация не принимается только по субъективному ощущению.

## Этап 1. Убрать блокирующие операции из event loop

1. Перевести БД на настоящий async SQLAlchemy (`create_async_engine`, `async_sessionmaker`, драйвер `asyncpg` для PostgreSQL и `aiosqlite` локально).
2. Настроить пул через окружение и начать консервативно: `pool_size=10`, `max_overflow=10`, `pool_timeout=3`, `pool_recycle`; окончательные значения выбрать по метрикам, а не увеличить безусловно.
3. Не выполнять `commit` после операций только для чтения. Транзакции записи делать короткими, с rollback при ошибке.
4. Вынести тяжёлые резервные копии и прочие файловые/CPU-задачи из event loop; уже вынесенный backup оставить и покрыть метрикой длительности.
5. Добавить таймауты SQL и тест, при котором искусственно медленная БД не останавливает heartbeat и чат.
6. Для SQLite явно оставить режим разработки: запуск нагрузочного профиля и production-конфигурации должен требовать PostgreSQL.

**Выход этапа:** при задержке БД 500 мс event-loop lag остаётся в SLO, а чат между уже подключёнными игроками продолжает работать.

## Этап 2. Ограничить стоимость синхронизации мира

1. Завести индексы `client_by_uid` и `clients_by_location`, обновляемые при подключении, переходе между локациями и отключении. Получение игрока и аудитории локации станет O(1).
2. Снизить серверный snapshot tick с 10 до 5 Гц, сохранив клиентскую интерполяцию; входящие позиции принимать с серверным rate limit и объединять, оставляя только последнее состояние игрока к следующему tick.
3. Не собирать один и тот же публичный объект по одному разу для каждого получателя: один раз сериализовать состояние каждого игрока за tick.
4. После baseline выбрать модель рассылки:
   * для 100 игроков обычно достаточно одного snapshot на локацию, отправляемого всем её участникам;
   * если худший сценарий всё ещё не проходит SLO — перейти на interest management по пространственной сетке и слать только игроков в соседних ячейках;
   * для дальнейшего снижения трафика — delta updates плюс редкий полный snapshot для восстановления.
5. Не отправлять неизменившиеся snapshots. Добавить sequence number и серверное время, чтобы клиент мог отбрасывать устаревшие пакеты и измерять задержку.

**Выход этапа:** худший сценарий со 100 игроками в одной локации проходит SLO; CPU и исходящий трафик не растут квадратично при сравнении ступеней 25/50/100.

## Этап 3. Изолировать медленных клиентов

1. Для каждого WebSocket создать отдельную ограниченную исходящую очередь и одну sender-задачу. Обработчики только ставят события в очередь и никогда не ждут физическую отправку всем получателям.
2. Разделить классы событий:
   * `chat`, PvP-результат, приглашения и системные сообщения — надёжная FIFO-очередь;
   * snapshots позиций — coalescing: старый неотправленный snapshot заменяется новым;
   * служебные обновления группы — допускают замену последним состоянием.
3. Задать лимит одновременно в сообщениях и байтах. При переполнении сначала удалять устаревшие coalescable-события; если надёжная очередь не освобождается — закрывать только медленного клиента с явным кодом и метрикой.
4. Сериализовать общий payload один раз (`send_bytes`), а не выполнять JSON-кодирование для каждого сокета.
5. Корректно отменять sender-задачу и очищать индексы/очереди при disconnect, ошибке авторизации и shutdown.

**Выход этапа:** клиент, который не читает сокет, не ухудшает p99 чата/PvP остальных 99 игроков и отключается предсказуемо по политике backpressure.

## Этап 4. Сделать чат и PvP устойчивыми

### Чат

1. Сохранить серверный rate limit, но хранить его по стабильному `uid`, а не только внутри конкретного соединения; добавить небольшой burst и отдельные лимиты для world/DM.
2. Адресовать DM по `uid`, а ник использовать только для отображения. Текущий поиск по нику неоднозначен и требует обхода всех клиентов.
3. Ввести монотонный ID сообщения и подтверждение постановки в серверную очередь. Клиент может безопасно повторить запрос с тем же ID после reconnect, не создавая дубль.
4. Историю мирового чата для одного процесса оставить кольцевым буфером. Перед горизонтальным масштабированием перенести publish/history в Redis Streams или PostgreSQL; личные сообщения хранить согласно отдельно принятой политике приватности и retention.

### PvP

1. Обрабатывать события каждого игрока последовательно через actor/lock по `uid`, чтобы два одновременных удара или сообщения о смерти не дали двойной результат.
2. Добавить `fight_id`/`hit_id`, sequence number и идемпотентность завершения боя. Уникальность результата смерти закрепить ограничением в БД или атомарным conditional update.
3. Перенести HP и решение о смерти на сервер либо, как минимальный промежуточный шаг, проверять накопленный сервером урон. Нельзя считать клиентское `pvp_dead` единственным доказательством результата.
4. Запись статистики смерти выполнять одной короткой транзакцией с блокировкой/условным обновлением строк обоих игроков. Повтор события должен возвращать прежний результат, а не начислять убийство снова.
5. Хранить cooldown в монотонном времени процесса; регулярно очищать данные отключённых игроков и старые пары.

**Выход этапа:** тесты гонок подтверждают единственное начисление убийства, порядок событий одного боя и отсутствие дублей при reconnect/retry.

## Этап 5. Жизненный цикл и отказоустойчивость

1. Добавить `/live` (процесс жив) и `/ready` (миграции завершены, БД доступна, фоновые sender/world задачи работают). Текущий `/health` оставить совместимым или направить на liveness.
2. Реализовать graceful shutdown:
   * перестать принимать новые соединения;
   * уведомить клиентов о reconnect;
   * дать надёжным очередям короткое время на drain;
   * закрыть WS, отменить и дождаться фоновых задач;
   * закрыть DB engine.
3. Ограничить время неаутентифицированного WebSocket (например, 5 секунд), число соединений с одного IP/uid и размер/частоту входящих сообщений.
4. Периодически удалять просроченные приглашения, rate-limit buckets, `last_seen`, PvP pair/cooldown и другие временные записи.
5. Запустить soak-тест на 6–12 часов, включая reconnect storm, временную задержку БД и один рестарт процесса.

**Выход этапа:** rolling restart не создаёт каскадных ошибок; после soak-теста нет монотонного роста памяти или задач.

## Горизонтальное масштабирование — только после успешного single-node теста

Для цели в 100 игроков предпочтителен один хорошо измеренный процесс: это проще и сохраняет локальный порядок событий. Если CPU, доступность или дальнейший рост требуют нескольких экземпляров, сначала нужно убрать зависимость от локальной памяти:

1. sticky routing по локации/игроку для WebSocket;
2. Redis для presence, rate limits, pub/sub и маршрутизации событий между экземплярами;
3. владелец (room worker) для каждой локации, который единолично упорядочивает позиции и PvP;
4. PostgreSQL как источник долговременной истины, Redis — только для эфемерного состояния;
5. fencing token/lease при передаче локации другому worker, чтобы два процесса не считали один бой одновременно;
6. тест принудительной потери worker и автоматического переподключения клиентов.

Запуск нескольких экземпляров **до** этого этапа запрещён: локальные `clients`, `parties`, чат и PvP-состояние дадут разные версии мира.

## Порядок поставки

Каждый пункт выпускается небольшим PR с нагрузочным отчётом до/после:

1. метрики, структурированные логи и нагрузочный стенд;
2. настоящий async-доступ к PostgreSQL;
3. индексы подключений, coalescing входящих позиций и оптимизированные snapshots;
4. очереди отправки и backpressure;
5. идемпотентные чат/PvP-события и серверное состояние боя;
6. readiness, graceful shutdown, уборка временного состояния и soak-тест;
7. решение о необходимости Redis/multi-node на основании измерений.

Для каждого PR обязательны unit-тесты изменённой логики, интеграционный тест WebSocket и ступенчатые прогоны 25/50/100. Откат выполняется feature flag для нового broadcaster/очередей; изменение схемы БД должно быть backward-compatible как минимум на один релиз.

## Итоговый чек-лист готовности

* Все SLO выполнены в трёх последовательных 30-минутных прогонах со 100 игроками.
* Пройден худший сценарий одной локации и сценарий медленного клиента.
* Пройден reconnect storm: 100 переподключений с jitter без каскадного отказа.
* Повтор `hit_id`, `fight_id` или chat event ID не создаёт дубль.
* Замедление БД не блокирует heartbeat и уже установленные чат-соединения.
* После 6–12 часов нет утечки памяти, задач, очередей и временных словарей.
* Дашборд и алерты проверены искусственным превышением порогов.
* Есть документированный rollback и отчёт baseline → result с CPU/RAM/network/latency.
