# Нагрузка: как включить, проверить и откатить

## Переменные Railway

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `METRICS_TOKEN` | пусто (выкл.) | доступ к `/metrics`; задай длинную случайную строку |
| `WORLD_HZ` | 10 | частота снимков мира; 5 — вдвое меньше трафика, если клиент интерполирует |
| `VIEW_RADIUS` | 0 (вся локация) | слать только игроков ближе радиуса; включать после проверки миникарты |
| `WS_MAX_PER_UID` | 3 | вкладок одного игрока одновременно |
| `WS_IN_RATE` / `WS_IN_BURST` | 60 / 120 | входящих сообщений с сокета в секунду / всплеск |
| `WS_MAX_QUEUE_MSGS` / `WS_MAX_QUEUE_BYTES` | 400 / 524288 | предел очереди клиента; при переполнении — отключение с кодом 4008 |
| `WS_SEND_TIMEOUT` | 10 | секунд на одну отправку, дальше клиент считается зависшим |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` | 10 / 10 | пул PostgreSQL (и число потоков базы) |
| `DB_STATEMENT_TIMEOUT_MS` | 5000 | зависший SQL-запрос обрывается |
| `LOADTEST` | пусто | `1` только на staging: боты получают PvP-уровень |

Healthcheck в Railway: путь `/ready` (503, пока сервер стартует или база недоступна). `/health` и `/live` — просто «жив».

## Прогон

1. Staging-сервис с PostgreSQL, `ENV_NAME=staging`, `LOADTEST=1`, `METRICS_TOKEN=...`, свой тестовый бот.
2. Короткая проверка: `python tools/loadtest.py --url https://<staging> --bot-token <токен staging-бота> --players 25 --ramp 10 --duration 60 --metrics-token <...>`
3. Ступени 25 / 50 / 100, затем `--one-loc` (худший случай). Отчёты `loadtest-report.json` сохранять рядом с PR.
4. Цели — в `docs/server-load-plan.md` (SLO). Тест печатает OK / НЕ ВЫПОЛНЕНО.

## Коды закрытия WebSocket

| Код | Причина |
| --- | --- |
| 4001 | нет авторизации за `WS_AUTH_TIMEOUT` или неверный initData |
| 4003 | открыта ещё одна вкладка сверх `WS_MAX_PER_UID` |
| 4008 | клиент не успевает читать (очередь переполнена или отправка зависла) |
| 4009 | поток сообщений сверх лимита |
| 1012 | сервер перезапускается — переподключиться |
